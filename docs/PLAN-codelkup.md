## 0. 本计划书改了什么（相对原 TECH-DESIGN）

原技术方案是在"不掌握本机环境"的前提下写的。实测环境后，有 **6 处必须修订**：

| # | 原文档 | 实测 / 核实结果 | 修订决定 | 证据等级 |
|---|---|---|---|---|
| 1 | Java 17 | 本机 **JDK 21.0.11**（Temurin，`D:\jdk\jdk-21`） | **用 Java 21**。21 是 LTS，Spring Boot 3.5/4.x 均官方支持 17–25 | ① 官方 |
| 2 | Spring Boot **3.3.x** | **3.3.x 已于 2025-06-30 OSS EOL，无任何补丁** | **改用 3.5.16**（3.x 末版，也是 3.x 唯一有企业支持到 2032 的线） | ① 官方 |
| 3 | 未指定安全线 | 4.x 为当前主线：4.0（2025-11 发布，OSS 至 2026-12-31）、4.1（2026-06 发布，OSS 至 2027-07） | **不上 4.x**，理由见 §1.2 | ① 官方 |
| 4 | Redis 7.x（V0.1 就要用） | **本机未装 Redis**，`redis-cli` 不存在 | Docker 起容器（守护进程已验证可用） | — |
| 5 | MySQL 8.0 | 8.0.37 已装，root 有密码（需配置） | 沿用，密码走 `.env` | — |
| 6 | Elasticsearch 8.x | 原文档称"4GB **显存**笔记本吃紧" | **概念错误**：ES 吃 JVM 堆与磁盘 IO，与显存无关。MVP 不上 ES 的结论不变，但理由要改对 | — |

> **关于第 2、3 条的取舍逻辑（这是本项目要能讲清的一段）**：
> 原文档写"3.3.x 是企业真实在用的版本线，不追 4.x"——这句话在 2026-09 已经**不成立**，3.3 已停更一年。
> 但"不上 4.x"的结论**依然正确**，理由换了：4.x 基于 Spring Framework 7，基线升到 Jakarta EE 11、Jackson 3，迁移会牵动 Hibernate / Jackson / Tomcat。
> **3.5.16 是当前"既在支持期、生态最熟、踩坑最少"的交叉点**——这才是真正的甜点区。这个判断比原文档的原始理由可靠。

### 1.2 为什么不上 Spring Boot 4.x（虽然它是受支持主线）

| 维度 | 3.5.16 | 4.1.1 |
|---|---|---|
| OSS 支持 | ❌ 已结束（2026-06-30） | ✅ 至 2027-07 |
| 企业支持 | ✅ 至 2032-06 | ✅ 至 2028-07 |
| 基线 | Spring Framework 6.2 | Spring Framework 7.0 |
| Jakarta EE | 9 | **11** |
| Jackson | 2.x | **3.x（默认）** |
| 生态资料 | 极多（3.x 共存期 5 年积累） | 少，中文资料尤其少 |
| 面试官熟悉度 | 高 | 中（4.x 才 10 个月） |

**决策：用 3.5.16。**

理由：本项目的目标是**求职作品**，不是生产系统。3.5.16 有企业支持兜底（到 2032），生态资料多到遇错必能搜到答案，面试官看到 3.5 不需要额外解释。
而 4.x 的收益（gRPC、OTel 改进、SSRF 防护）本项目**一个都用不上**，成本（Jackson 3 迁移、Jakarta EE 11）却是实打实的。

> 📌 **但要在简历/面试里主动说明这一点**——"为什么不用 Spring Boot 4"本身就是个能体现技术判断力的加分回答。
> 反过来，如果简历写"3.3.13"而面试官知道它 2025 年就停更了，会被追问"你不知道 3.3 已经 EOL 了吗"，那是减分。

### 1.3 明确不引入的（沿用原文档结论，保留）

- ❌ 微服务 / Spring Cloud（单人项目运维成本 > 收益）
- ❌ MQ（RocketMQ / Kafka）——论坛量级用不上，Spring Event 足够
- ❌ Elasticsearch（MVP 阶段）——**理由修正**：不是"显存不够"，而是"多一个 1GB 堆的中间件，零额外依赖的 MySQL ngram 已能覆盖 MVP 需求"
- ❌ 富文本编辑器、移动端 App、付费体系（沿用原文档判断）

### 2.3 MySQL 全文检索前置校验（S4 之前必须做）

原方案依赖 `FULLTEXT ... WITH PARSER ngram`。**这依赖不是默认开的**，取决于 build 配置：

```sql
SHOW VARIABLES LIKE 'ngram_token_size';   -- 若为空/报错，说明该 ngram 插件不可用
```
- 若可用 → 按原方案走 ngram
- 若不可用 → 降级方案：`LIKE` + 应用层分词，或引入轻量分词库（如 HanLP / IK）在写入时预生成 `content_index` 字段

> ⚠️ **这条不验证就写代码，S4 会卡住返工。** 建议排在 S0 一起做。

| 项 | 取值 | 依据 |
|---|---|---|
| 身份 | 27 届本科，大四上 | 用户背景 |

理由：MVP 无并发压力，批量缓冲是过早优化；且"先朴素实现 → V0.2 优化"正好是原文档自己主张的叙事策略（"优化前的版本本身就是素材"）。

## 5. 关于周期的坦诚说明 ⚠️

**总周期：S0~S5 合计约 6.5 周 × 8.5h ≈ 55 小时。**

但这里有个必须说清的问题：

> 今天是 **2026-09-24**。6.5 周后是 **11 月中旬**。
> 27 届秋招的核心投递窗口就在 9~11 月，多数公司 10 月底进入收尾。
> **按计划完整做完，项目上线时间 ≈ 秋招结束时间。**

这不是排期问题，是**"按完整产品思路规划一个求职作品"**导致的错位。

### 建议：分两段交付，提前投递

| 阶段 | 内容 | 时间点 | 简历可写内容 |
|---|---|---|---|
| **第一段（S0~S3）** | 骨架 + 认证 + 内容 + 互动计数 | **约 4 周 → 10 月下旬** | "完成核心闭环，含 Redis 计数与防重设计" |
| **投递** | **不等全部做完，立即投递** | 10 月下旬 | 用已完成部分写简历 |
| 第二段（S4~S5） | 检索 + 关注 + 容器化 + 压测 | 11 月中 | 简历更新"追加全文检索与压测报告" |

**理由**：
